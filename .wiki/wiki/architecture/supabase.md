## 요약

Local Supabase/Auth 기반과 staging Auth promotion에 더해 account Logbook/Planbook schema, typed repository, local-first outbox와 resumable guest data claim 경계가 구현됐다. Hosted project `mclvhwzsuvsxjerdouka`는 staging 전용이며 production이 아니다. Account-data migrations와 claim Edge Function은 hosted staging automated verifier를 통과했다. Physical claim, production과 account deletion은 별도 승격 gate다.

## 현재 상태

Root `supabase/`에는 local config, Auth foundation과 account-data migration, pgTAP/REST/Edge Function harness, hosted 환경 변수에서 격리된 local CLI wrapper가 있다. `packages/supabase`에는 generated database type, typed client factory, Auth repository와 typed account Logbook/Planbook/profile 및 guest claim repository가 있다. Mobile에는 native Auth, principal-partitioned local repositories, account outbox/sync와 resumable claim service가 있다. 앱 내 account deletion은 아직 없다. 사용자가 실기기 foreground에서 약 4분 Watch 세션의 pairing, 모바일 자동 import, local save 뒤 Watch `synced` 전환을 확인했지만 이는 Auth 도입 전 기준선이며 post-Auth regression, reconnect, background, killed-app, large transfer 증거는 아니다.

Divenary rename 뒤 `com.divenary.app`과 embedded `com.divenary.app.watchkitapp`의 generic physical-device Debug build, automatic provisioning, strict signature verification이 통과했다. Signed iPhone app에만 Apple Sign In entitlement가 있고 Watch app에는 없다. Main checkout의 ignored development env에는 유효한 Google iOS Client ID가 있으며, 여기서 산출한 reversed callback scheme을 iPhone Debug/Release에 설정했다. 이전 worktree에는 ignored env가 복사되지 않아 이를 Client ID 부재로 잘못 기록했다. Watch에는 Google callback을 넣지 않는다. Apple provider 설정은 사용자 보고 상태이며 hosted provider audience, production legal URL/current pointer와 실제 Auth token exchange는 physical matrix에서 검증해야 한다.

Auth는 iOS native Google/Apple login과 Keychain-compatible session을 구현한다. 데이터베이스는 `app_memberships`, immutable `legal_documents`, kind별 `current_legal_documents` pointer, append-only `consent_records`를 분리한다. User id 인자가 없는 status RPC가 현재 필수 동의 coverage를 계산하므로 membership이 이미 있어도 새 current version에는 재동의해야 한다. Completion RPC는 current terms/privacy exact set만 원자적으로 기록하고 active Auth session을 확인한다. Login 자체는 guest 데이터를 삭제하지 않으며, 사용자가 account claim 또는 기기에 유지를 선택할 수 있는 claim state가 별도로 준비된다.

Account data schema는 `dive_logs`, `dive_plans`, private `dive-profiles` bucket을 사용한다. Row는 `(user_id, local_id)`로 한 소유자 안에서 고유하며 positive `revision`과 payload digest를 가진다. RLS는 `auth.uid()`와 membership을 함께 확인한다. 전체 Watch profile은 list row에 넣지 않고 `<user_id>/claims/...` staging 또는 `<user_id>/logs/...` account object path 아래 JSON으로 저장한다.

Guest claim은 normal account row와 분리된 `guest_claim_batches`/`guest_claim_records`에 immutable manifest와 record/profile digest를 staging한다. Edge Function은 authenticated user와 exact profile bytes를 검증한 뒤 service-role finalizer를 호출한다. Finalizer는 expected count, 관계, digest와 기존 local ID를 한 transaction에서 검사하고 account rows를 publish한다. 같은 committed batch 재호출은 idempotent하다. Public wrapper는 먼저 batch, 현재 batch records, 같은 owner/local ID의 모든 plan, 모든 log 순서로 row lock을 얻고 각 candidate 집합을 안정된 ID 순서로 잠근다. Private publication 뒤에는 새로 materialize됐거나 첫 snapshot에서 보이지 않았던 unique-key winner까지 포함하도록 모든 plan과 모든 log를 같은 순서로 다시 잠근다. 두 candidate phase 모두 active와 soft-deleted row를 포함한다. Byte-level digest가 다르더라도 active profiled Watch log의 owner/local ID, relation, profile revision/digest/count와 모든 사용자 의미 field가 같고 차이가 동등한 `timestamptz`, source-derived float readback, 세 import bookkeeping timestamp뿐이면 phase-one lock 안에서 canonical row의 payload 표현과 digest를 staged 표현으로 정규화한다. Canonical ID, owner, local ID, profile path/revision과 relation은 바꾸지 않는다. 그 뒤 기존 private strict digest 검증, phase-two lock/revalidation과 canonical target remap을 그대로 실행하므로 이후 실패는 정규화와 publication을 함께 rollback한다. Soft-deleted row, title/site/rating/notes, profile tuple, relation 또는 다른 JSON 차이는 계속 whole-batch conflict다. Finalizer는 committed batch/record와 claim profile object를 삭제하지 않고 idempotent readback과 audit 근거로 보존한다. Auth user deletion 시 database claim row는 foreign key로 cascade되지만 remote Storage profile object는 자동 삭제되지 않는다. Account deletion과 privileged object cleanup이 아직 구현되지 않았으므로 이 object는 보존되며, cleanup은 future release gate다.

Supabase table은 RLS만으로 노출되지 않는 2026 Data API 권한 모델을 적용해 최소 `GRANT`도 migration에 명시한다. Session bootstrap은 `getSession()`만 신뢰하지 않고 online claims/user/status 검증을 수행한다. `getClaims()` 또는 `getUser()` transport failure 때만 unexpired stored session evidence와 같은 user의 마지막 server-verified complete cache가 정확히 일치하면 local-only offline state를 허용한다. Invalid session, server rejection 또는 onboarding-status RPC 실패는 offline fallback 근거가 아니다. Client concurrency는 설치된 `auth-js@2.110.2`의 기본 lockless single-flight/commit guard를 사용하며 deprecated `processLock` custom option은 추가하지 않는다.

로컬 Supabase 명령은 격리된 launcher를 통해 실행한다. Root local CLI wrapper와 type generator/REST harness의 sanitized child environment는 shell에 주입된 다른 hosted project의 `SUPABASE_PROJECT_ID`와 access token을 제거하므로 local stack, migration test, type generation이 repository `config.toml`의 독립 project context만 사용한다. 일상적인 authenticated 개발은 실제 Docker local Supabase에서 `yarn supabase:start` 또는 `yarn supabase:reset`, `yarn mobile:auth:local:prepare`, `yarn mobile:ios:local` 또는 `yarn mobile:android:local`로 수행하고, Metro만 필요할 때는 `yarn mobile:start:local`을 사용한다. Mobile bundle은 normalized local/staging/release mode를 inline하며 알 수 없는 explicit mode는 build configuration 오류로 중단한다. Local Auth client는 `__DEV__`, allowlisted HTTP loopback endpoint와 fixture credential을 모두 요구한다. Staging Auth client는 고정된 `https://mclvhwzsuvsxjerdouka.supabase.co` origin에서만 social Auth를 구성하고, release mode는 development Auth client를 만들지 않는다. Local Metro는 전용 port `8082`와 selected inline environment의 one-way cache fingerprint를 사용하며 fixture prepare는 그 port를 선점할 수 있을 때만 credential을 rotate한다. fixture가 만드는 ignored `apps/mobile/.env.local`은 mode `0600`의 local-only 파일이며 credential을 문서나 tracked configuration에 기록하지 않는다.

Hosted promotion 명령은 local path와 명시적으로 분리한다. `mclvhwzsuvsxjerdouka`는 staging 전용 project ref이며 migrations `20260713135707`, `20260719130604`, `20260719134648`, `20260720230000`, `20260729200000`, `20260729210000`, `20260729220000`, `20260730111944`와 `finalize-guest-claim` Edge Function이 배포됐다. current terms/privacy는 `2026-07-18-staging.1`, `2026-07-18T00:00:00.000Z`, promotion commit에 고정된 immutable HTTPS URL이다. Guard는 정확한 project ref만 허용한다. Auth verifier는 exact legal row/effective time/URL, `get_onboarding_status() -> jsonb` metadata, anonymous `42501` denial과 Google/Apple enabled flag를 확인한다. Guest-claim verifier는 disposable user 두 명으로 owner RLS, private profile object, atomic finalization, committed payload digest, idempotency, equivalent cross-device batch의 canonical-ID 조정, timestamp·source float·import bookkeeping 표현만 다른 profiled Watch log의 semantic canonical reuse, 사용자 의미 field divergence와 soft-deleted equivalent collision의 rollback을 확인하고 종료 시 fixture를 정리한다. 배포 chronology에서 `20260729200000` 적용 때는 Function을 재배포하지 않았고, 이후 commit `fa68f0f`의 exact-argument guard로 unchanged source를 재배포했다. `20260729210000`, `20260729220000`, `20260730111944` 적용 때는 source가 계속 unchanged였으므로 추가 Function 배포 없이 기존 hosted Function이 새 wrapper를 호출했고 verifier가 각각 통과했다. `20260730111944` push 뒤 local/remote migration history도 일치했다. Local multi-session harness도 post-publication winner lock 뒤 divergent updater 대기와 divergence 재검증 rollback을 실제 PostgreSQL session으로 통과했다. Hosted staging은 실제 provider callback용 `apps/mobile/.env.development`를 쓰며 local password fixture와 섞지 않는다.

같은 verified email의 OAuth identity는 Supabase Auth의 automatic linking을 따르되 app code는 email을 비교하거나 manual linking UI를 제공하지 않는다. Authorization은 `auth.uid()`만 사용한다. Email/password, magic link, SMS, Android native Auth, nickname/profile/friends, marketing consent는 범위 밖이다.

## 상세

Supabase가 도입될 때 책임은 다음과 같다.

- `supabase/`: local configuration, migration, RLS, seed, database test, privileged account deletion boundary.
- `packages/supabase`: generated database type, typed client factory, Auth와 typed Logbook/Planbook/profile/guest claim repository. React Native UI와 native provider SDK에는 의존하지 않는다.
- `apps/mobile`: Keychain-compatible Auth, principal-scoped local repository, durable outbox/sync, account cache와 guest claim orchestration을 소유한다.
- Watch app: 기존 local capture와 iPhone sync만 담당한다. Supabase client, account id, cloud business logic을 갖지 않는다.

로컬 principal은 `guest`와 `user:<uuid>`로 분리한다. Guest는 claim 전까지 local-only다. Account 연결은 persistent immutable snapshot/manifest와 bounded batch를 사용해 remote record/profile write와 readback, atomic finalization과 committed-batch readback을 검증한다. 그 snapshot은 base account local repository에 직접 publish/readback한 뒤 `cleanupPending`을 저장한다. Exact snapshot은 삭제하고 claim 중 변경된 guest row는 normal account local-first/outbox에 `pending` update로 저장·readback한 뒤 삭제한다. 모든 local cleanup이 끝나야 manifest를 `committed`로 저장하며, 중단되면 `cleanupPending`에서 재개한다. Deferred guest/account row의 기본 합성은 같은 local ID에서 account-copy-wins다. User 전환은 repository, outbox, manifest, profile을 user별 namespace로 격리하고 이전 principal의 React Query cache를 제거한다.

Logbook은 `(started_at desc, id desc)`, Planbook은 migration과 typed repository가 일치하는 `(created_at desc, id desc)` owner cursor와 기본 page size 30을 사용한다. Planbook UI의 `plannedAt` 기반 표시 정렬과 remote pagination cursor는 별개다. 목록에는 typed metadata와 최대 160개 preview sample만 포함한다. 전체 1Hz profile은 private `dive-profiles/<user_id>/logs/<dive_log_id>/<content_revision>.json` immutable object로 저장하고 detail에서만 다운로드한다. Claim 중에는 `<user_id>/claims/<batch_id>/<target_record_id>/<content_revision>.json` 경로를 사용하며, 현재 finalizer는 commit 뒤 이 object를 account path로 옮기거나 삭제하지 않는다.

Signed-in write는 local save 뒤 idempotent outbox가 전달한다. Remote row `revision`이 expected revision과 다르면 local mutation을 `conflict`로 보존하고 remote latest를 가져온다. Watch `session.syncStatus: synced`는 iPhone local import acknowledgement이고 remote cloud 성공과 독립적이다.

3D의 계정 삭제는 앱 안에서 재확인 뒤 즉시 영구 삭제한다. 7일 유예 soft deletion/recovery는 후속 기능이다. `service_role`과 provider secret은 mobile bundle에 두지 않는다. Local seed의 `.invalid` legal URL은 test fixture이며 production 법률 문서가 아니다.

Stable Divenary App ID, signed provisioning과 Google iOS client/reversed callback은 확보됐다. 사용자는 physical iPhone에서 Apple login 성공을 확인했지만 Google physical login, cancellation/repeat, session restore와 re-consent는 아직 통과로 기록하지 않는다. Account-data migrations와 `finalize-guest-claim`은 hosted staging automated verifier를 통과했지만 physical claim 검증 증거는 아직 없다. Production project, production legal document와 앱 내 즉시 영구 account deletion은 future work이며 이 gate 전에는 release하지 않는다.
