# Supabase Auth Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Build Wave 3A: local Supabase development, generated database types, secure iOS-native Google/Apple login, and mandatory versioned terms/privacy onboarding without changing local-only Logbook/Planbook behavior.

**Architecture:** Root supabase/ owns migrations, seed data, database tests, and local configuration. packages/supabase owns generated types and provider-independent Auth/membership access; apps/mobile owns Keychain persistence, native provider credentials, the Auth state machine, navigation, and UI. Wave 3A deliberately leaves current repositories and cloudSyncStatus: notConfigured untouched so Auth is verified before remote dive data exists.

**Tech Stack:** Yarn 1.22.22, Supabase CLI 2.109.1, @supabase/supabase-js 2.110.2, @react-native-google-signin/google-signin 16.1.2, @invertase/react-native-apple-authentication 2.5.1, react-native-keychain 10.0.0, react-native-url-polyfill 3.0.0, React Native 0.85.3, React 19.2.3, React Navigation 7, Jest 29, pgTAP, Swift/Xcode.

## Global Constraints

- Use Yarn 1 only and pin every newly added package to its exact approved version; do not create another lockfile.
- iOS exchanges Google native ID tokens directly. Apple exchanges its ID token with the raw nonce whose hash was sent to Apple. Do not attach an unbound nonce to a Google token from the selected free SDK.
- Exclude email/password, magic link, SMS, browser OAuth, Android native Auth, nickname, avatar, friends, account linking, marketing consent, and 7-day soft deletion.
- Do not build manual linking/unlinking or compare provider emails in app code. Accept Supabase Auth automatic linking for OAuth identities with the same verified email; do not attempt to force provider-specific users.
- Store Supabase sessions in iOS Keychain. Never store provider access tokens, service_role, provider secrets, session tokens, or email addresses in logs or analytics.
- Of the Supabase configuration, bundle only the project URL and publishable key.
- Google web/iOS client IDs and reversed URL scheme are public identifiers and may also be bundled; Google/Apple secrets and `service_role` may not.
- Enable RLS on every exposed table. Derive authorization from auth.uid(), never user_metadata or provider email.
- First social sign-in must complete current required terms/privacy onboarding before active membership.
- Disable anonymous sign-in. A membership write RPC must also reject an `is_anonymous = true` JWT.
- Validate a restored session online with `getClaims()` and `getUser()` before treating it as authenticated. `getClaims()` may need the network for a JWKS cache miss or symmetric signing, so a transport failure is not an invalid-token verdict. `getSession()` alone is storage retrieval, not online authorization evidence.
- Use `processLock`, `autoRefreshToken: true`, and one AppState listener calling `startAutoRefresh()`/`stopAutoRefresh()`.
- Guest local data remains usable. Wave 3A does not claim, delete, upload, partition, or permanently hide it.
- Watch session.syncStatus: synced remains iPhone local-import acknowledgement and never waits for Supabase.
- Logbook/Planbook remain local-only with cloudSyncStatus: notConfigured through Wave 3A.
- The app remains a non-certified logging and review companion; Auth/cloud state cannot affect underwater safety behavior.
- Wave 3A is an internal checkpoint and must not ship to the App Store before Wave 3D adds in-app permanent account deletion.
- Create migrations with yarn supabase migration new; never hand-invent migration timestamps.
- Treat hosted Supabase provider configuration, real immutable terms/privacy URLs, stable owned bundle ID/App ID, Google OAuth clients, Apple signing, and a physical iPhone as an external promotion gate. Automated implementation may finish without falsely passing that gate.

- [ ] **Step 4: Implement schema and atomic onboarding**

The CLI-created migration must define immutable document versions plus a mutable current pointer:

~~~sql
create table public.app_memberships (
  user_id uuid primary key references auth.users(id) on delete cascade,
  onboarding_completed_at timestamptz not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table public.legal_documents (
  kind text not null check (kind in ('terms', 'privacy')),
  version text not null,
  effective_at timestamptz not null,
  document_url text not null check (document_url ~ '^https://'),
  primary key (kind, version)
);

create table public.current_legal_documents (
  kind text primary key check (kind in ('terms', 'privacy')),
  document_version text not null,
  foreign key (kind, document_version)
    references public.legal_documents(kind, version)
);

create table public.consent_records (
  user_id uuid not null references auth.users(id) on delete cascade,
  document_kind text not null,
  document_version text not null,
  agreed_at timestamptz not null default now(),
  primary key (user_id, document_kind, document_version),
  foreign key (document_kind, document_version)
    references public.legal_documents(kind, version)
);
~~~

Enable RLS on all four tables. Create owner `SELECT` policies on membership/consent and public `SELECT` policies on legal/current documents. Apply explicit 2026 Data API privileges:

~~~sql
revoke all on public.app_memberships, public.legal_documents,
  public.current_legal_documents, public.consent_records
  from public, anon, authenticated;
grant select on public.legal_documents, public.current_legal_documents
  to anon, authenticated;
grant select on public.app_memberships, public.consent_records
  to authenticated;
~~~

`get_onboarding_status()` is `SECURITY INVOKER`, `STABLE`, has `set search_path = ''`, accepts no user ID, and returns one JSON object with camelCase keys:

~~~ts
type OnboardingStatus = {
  isComplete: boolean;
  onboardingCompletedAt: string | null;
  requiredDocuments: Array<{
    kind: 'terms' | 'privacy';
    version: string;
    effectiveAt: string;
    documentUrl: string;
  }>;
  acceptedDocuments: Array<{ kind: 'terms' | 'privacy'; version: string }>;
};
~~~

Add a trigger on `current_legal_documents` that rejects a pointer when its target `effective_at > transaction_timestamp()`. Both RPCs validate that exactly one effective `terms` and one effective `privacy` pointer exist; otherwise they raise the stable server-configuration error `legal_configuration_invalid` rather than returning a misleading pending state.

`isComplete` is true only when `auth.uid()` has a membership and both current pointers have matching consent. `complete_onboarding(requested_documents jsonb)` is `SECURITY DEFINER`, has `set search_path = ''`, rejects null/anonymous users, parses JWT `session_id`, and requires an `auth.sessions` row whose `id` and `user_id` match the caller. It requires a JSON array whose distinct `(kind, version)` set is exactly the two current, already-effective rows, inserts consent and membership with `ON CONFLICT DO NOTHING`, and returns the same status shape in one transaction. Every relation/function reference is schema-qualified. Never upsert membership timestamps.

Use exact signature grants for both functions:

~~~sql
revoke execute on function public.get_onboarding_status() from public, anon;
revoke execute on function public.complete_onboarding(jsonb) from public, anon;
grant execute on function public.get_onboarding_status() to authenticated;
grant execute on function public.complete_onboarding(jsonb) to authenticated;
~~~

export type RequiredLegalDocument = {
  kind: 'terms' | 'privacy';
  version: string;
  effectiveAt: string;

export type StoredSessionEvidence = {
  session: Session;
  userId: string;
  expiresAt: number;

export type AuthRepositoryErrorKind =
  | 'network'
  | 'invalid-session'
  | 'server';

export class AuthRepositoryError extends Error {
  readonly kind: AuthRepositoryErrorKind;

  constructor(
    kind: AuthRepositoryErrorKind,
    options?: { cause?: unknown },
  ) {
    super('Authentication operation failed', options);
    this.name = 'AuthRepositoryError';
    this.kind = kind;
  }
}

export interface AuthRepository {
  signInWithIdToken(input: SocialIdTokenInput): Promise<Session>;
  getStoredSessionEvidence(): Promise<StoredSessionEvidence | undefined>;

  ): Promise<OnboardingStatus>;
  signOut(): Promise<void>;
  startAutoRefresh(): void;
  stopAutoRefresh(): void;
  subscribe(listener: (session: Session | null) => void): () => void;
}
